# NochOtel — план переработки

Цель переработки: превратить текущую учётную систему в полноценный продукт с двумя «лицами» —
**рабочий портал персонала** (`/app`) и **мобильный кабинет вахтовика** (`/me`), плюс карта,
социальные взаимодействия и нормальный контент о доме и посёлке. Система закрытая: весь доступ
только по логину, у каждого свой профиль.

---

## 1. Что уже есть (аудит текущей базы)

**Стек:** Vue 3 + Vite + Pinia + Router (`web/`), Node + Express + SQLite (better-sqlite3) + JWT (`server/`).
Токены оформления Modrinth (тёмная/светлая тема) в `web/src/styles/tokens.css`.

**Роли:** `admin` / `editor` = персонал (портал `/app`), `viewer` = вахтовик (портал `/me`,
привязан к проживающему через `users.resident_id`). Автовыдача аккаунтов жильцам, блокирующая
смена пароля при первом входе. Анонимного доступа нет.

**Данные (server/db.js):** `hotels` (уже есть `latitude`/`longitude`, `settlement`, `rules`,
`check_in`/`check_out`) → `rooms` → `beds`; `residents` (about, photo); `placements` (стадии
expected/checked_in/checked_out/cancelled); `statuses` с цветами; `amenities` + связки;
`places` (что рядом); `images` (галереи по URL); `reviews` (оценки дома); `room_blocks` (ремонт);
`room_issues` (заявки «сломалось в номере»); `audit_log`.

**Персонал:** дашборд, шахматка (Rack), поиск свободных мест (availability), план этажа,
номерной фонд, проживающие, пользователи, аналитика с SVG-графиками, журналы, Excel-отчёты/импорт.

**Вахтовик:** хаб `/me` + размещение, соседи, дом/посёлок, профиль; отзыв о доме; заявки на ремонт.

**Вывод:** ядро учёта готово и его не трогаем. Переработка — это (а) карта, (б) мобильный UX
вахтовика, (в) социальный слой, (г) контент о доме/посёлке, (д) чистка схемы и деплой.

## 2. Целевая структура продукта

```
NochOtel
├── /login                    единая точка входа
├── /app   — портал персонала (десктоп-first, плотный, рабочий)
│   ├── Дашборд               сводка + карта посёлков с загрузкой
│   ├── Карта                 интерактивная карта: дома → занятость (hover/клик)
│   ├── Бронирование          шахматка (есть)
│   ├── Свободные места       (есть)
│   ├── План этажа            (есть; + hover-поповеры занятости)
│   ├── Номерной фонд         (есть)
│   ├── Проживающие           (есть)
│   ├── Заявки                очередь room_issues с тредами и статусами
│   ├── Объявления            публикация на дом/на все дома
│   ├── Аналитика / Журналы / Пользователи (есть)
└── /me    — кабинет вахтовика (mobile-first, PWA)
    ├── Главная               лента: моё размещение, объявления, статус заявок
    ├── Мой дом               карта, галерея, правила, контакты, что рядом, отзывы
    ├── Соседи                профили соседей по комнате (с приватностью)
    ├── Заявки                мои заявки на ремонт + переписка по ним
    └── Профиль               данные, фото, «о себе», приватность, пароль
```

Принцип: **персоналу — плотность и скорость, вахтовику — простота и крупные элементы.**
Это два разных UI на одном API и одной дизайн-системе.

## 3. Переработка базы данных

Миграции в стиле уже существующих (idempotent `addColumn` / `CREATE TABLE IF NOT EXISTS` в `db.js`).

### 3.1 Чистка
- `users.role`: убрать `'resident'` из CHECK (пересоздание таблицы, как уже делали для `resident_id`).
- `hotels.latitude` / `longitude`: TEXT → REAL (пересоздание или новые колонки + перенос).
- Индекс `idx_placements_resident ON placements(resident_id)` — под ленту вахтовика и отчёты.

### 3.2 Гео (под карту)
- `places`: `+ latitude REAL, longitude REAL, icon TEXT` — чтобы «что рядом» показывалось на карте.
- `hotels`: остаётся точкой на карте посёлка; посёлок группируем по полю `settlement` (отдельная
  таблица не нужна для масштаба задачи).

### 3.3 Социальный слой
```sql
CREATE TABLE announcements (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    hotel_id   INTEGER REFERENCES hotels(id) ON DELETE CASCADE,  -- NULL = все дома
    title      TEXT NOT NULL,
    body       TEXT NOT NULL,
    pinned     INTEGER NOT NULL DEFAULT 0,
    created_by INTEGER REFERENCES users(id) ON DELETE SET NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE issue_comments (                                    -- переписка по заявке
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    issue_id   INTEGER NOT NULL REFERENCES room_issues(id) ON DELETE CASCADE,
    user_id    INTEGER REFERENCES users(id) ON DELETE SET NULL,
    text       TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```
- `reviews`: `+ reply TEXT, reply_at TEXT` — ответ администрации на отзыв.
- `residents`: `+ show_contacts INTEGER NOT NULL DEFAULT 0` — показывать ли телефон соседям
  (приватность: сосед всегда видит имя/фото/«о себе», телефон — только по согласию).
- «Непрочитанное» без отдельной таблицы: `users.announcements_seen_at TEXT` — бейдж считается
  как `COUNT(*) WHERE created_at > seen_at`.

### 3.4 Контент о доме
```sql
CREATE TABLE hotel_info_sections (        -- структурированные блоки страницы дома
    id       INTEGER PRIMARY KEY AUTOINCREMENT,
    hotel_id INTEGER NOT NULL REFERENCES hotels(id) ON DELETE CASCADE,
    kind     TEXT NOT NULL,               -- 'schedule' | 'contacts' | 'rules' | 'custom'
    title    TEXT NOT NULL,
    body     TEXT NOT NULL,
    sort     INTEGER NOT NULL DEFAULT 0
);
```
Сюда — распорядок (столовая, баня, транспорт до цеха), полезные телефоны (комендант, медпункт,
диспетчер), правила проживания. Персонал редактирует в «Номерном фонде», вахтовик видит в «Моём доме».

### 3.5 Файлы вместо URL
Сейчас фото — только по URL. Добавить загрузку через `multer` в `data/uploads/`, раздачу через
`/uploads/*` (за auth-middleware — система закрытая). Использовать для: галерей домов/номеров,
фото профиля, фото к заявке (`room_issues + photo TEXT`).

## 4. Этапы работ

### Этап 0 — фундамент (короткий)
1. Миграции из раздела 3.1 (чистка ролей, REAL-координаты, индексы).
2. Загрузка файлов (multer) + перевод `images`/`residents.photo` на неё (URL оставить как fallback).
3. PWA-минимум: `manifest.json`, иконка, `theme-color`, мета-viewport — чтобы `/me` ставился
   на домашний экран телефона как приложение.

### Этап 1 — карта (главная «фишка» для защиты)
Библиотека: **Leaflet + OpenStreetMap** (лёгкая, бесплатная, работает с Vue без обвязки).

- **Персонал, страница «Карта»:** маркеры домов, цвет маркера = уровень загрузки
  (зелёный < 70 %, жёлтый 70–95 %, красный ≥ 95 %). Hover/клик → поповер: «Дом N: свободно
  X из Y мест, заездов сегодня Z» + кнопки «Шахматка», «План этажа». Данные — новый
  `GET /map` (агрегат по `hotels` + активные `placements` + `room_blocks` на сегодня).
- **Вахтовик, «Мой дом»:** мини-карта с его домом и точками `places` (столовая, медпункт,
  магазин) с иконками и расстояниями.
- **План этажа:** к существующим плиткам Plan.vue добавить hover-поповер (кто живёт, до какого
  числа, свободные койки) — это второй «элемент интерактивности» из ТЗ.
- Ввод координат: в форме дома/места — поле + кнопка «указать на карте» (клик по карте пишет
  lat/lng в форму).

### Этап 2 — мобильный кабинет вахтовика
Переработка `ResidentLayout.vue` и страниц `/me` под телефон:

- **Нижний таб-бар** (5 вкладок: Главная, Мой дом, Соседи, Заявки, Профиль) вместо верхней
  навигации; на десктопе таб-бар превращается в верхнюю навигацию (CSS-брейкпоинт).
- **Главная = лента**, а не решётка карточек: приветствие → карточка размещения (номер, койка,
  даты, сколько дней до выезда) → закреплённые объявления → активные заявки со статусами →
  быстрые действия («Сообщить о проблеме», «Оценить дом»).
- Крупные touch-цели (min 44 px), skeleton-загрузка, пустые состояния с иллюстрацией-иконкой,
  pull-to-refresh не нужен — кнопка обновления в шапке.
- Тёмная тема по умолчанию сохраняется (общежитие, вечер — уместно).

### Этап 3 — социальные взаимодействия
1. **Объявления:** персонал публикует (на один дом или на все), вахтовик видит в ленте,
   бейдж непрочитанных на табе «Главная». CRUD `GET/POST/DELETE /announcements`,
   `GET /me/announcements`.
2. **Заявки 2.0** (на базе `room_issues`): фото к заявке, тред комментариев (вахтовик ↔ персонал),
   таймлайн статусов «Новая → В работе → Починено», у персонала — общая очередь заявок по всем
   домам с фильтрами. Это главный «социальный» контур системы: житель реально общается с комендантом.
3. **Соседи:** карточки с фото, «о себе», должностью/организацией; телефон — только если сосед
   включил `show_contacts` у себя в профиле.
4. **Отзывы:** ответ администрации на отзыв (виден всем жильцам дома), средний рейтинг дома
   на карте и в аналитике (уже есть частично).

### Этап 4 — «Мой дом» как полноценная страница
Собрать из уже существующих данных + раздела 3.4: галерея (есть) → мини-карта (этап 1) →
рейтинг и отзывы (есть) → правила и часы заезда/выезда (есть) → блоки `hotel_info_sections`
(распорядок, телефоны) → «что рядом» списком и на карте. У персонала — редактирование всех
блоков на вкладке дома в «Номерном фонде».

### Этап 5 — деплой и многопользовательская работа
- **VPS** (любой дешёвый): Node за **nginx** (reverse proxy + gzip + HTTPS через certbot),
  процесс под **pm2** (или systemd). SQLite для десятков одновременных пользователей достаточно
  (WAL уже включён).
- **Бэкапы:** cron-копия `data/nochotel.db` (через `VACUUM INTO`) + папки `uploads/` раз в сутки.
- Секреты (`JWT_SECRET`, порт) — в `.env`; в репозитории `.env.example`.
- Для защиты практики хватит HTTP-деплоя на VPS + домен/IP; HTTPS — бонус.

## 5. Дизайн-принципы

- **Одна дизайн-система, два темпа.** Токены уже есть (`tokens.css`, brand = purple, dark/light).
  Персонал: плотные таблицы, много данных на экран. Вахтовик: одна колонка, крупный шрифт,
  карточки, максимум 1–2 действия на экран.
- **Цвет = статус.** Палитра статусов из БД (`statuses.color`) используется всюду одинаково:
  шахматка, план этажа, маркеры карты, бейджи заявок.
- **Иконки только lucide** через `Icon.vue` (уже сделано, эмодзи не возвращаем).
- **Пустые состояния и загрузка.** Каждый экран имеет skeleton и осмысленное пустое состояние
  («Заявок нет — всё работает 🎉» → без эмодзи: иконка + текст).
- **Доступность:** контраст по токенам, фокус-обводки, `aria-label` на иконочных кнопках.

## 6. Разделение на троих

| Роль | Зона | Основные задачи |
| --- | --- | --- |
| **A — Гео/интерактив** | карта | Leaflet, `GET /map`, страница «Карта» персонала, мини-карта в «Моём доме», координаты в формах, hover-поповеры плана этажа |
| **B — Кабинет вахтовика** | `/me` | мобильный layout + таб-бар, лента «Главной», «Мой дом», соседи с приватностью, PWA-манифест |
| **C — Бэкенд/соцслой/деплой** | server | миграции, загрузка файлов, объявления, заявки 2.0 (треды, фото, очередь у персонала), деплой + бэкапы |

Порядок: Этап 0 делается вместе (день), дальше этапы 1–3 идут параллельно по зонам,
этап 4 собирает результаты A и C в интерфейсе B, этап 5 — в конце.

| Метод | Путь | Кто | Назначение |
| --- | --- | --- | --- |

| PUT | `/hotels/:id/info` | staff | блоки hotel_info_sections |
